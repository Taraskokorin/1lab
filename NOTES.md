# Робочі нотатки

## ЛР 1. Середовище розробки .NET і перший застосунок Blazor

- Застосунок створено командою `dotnet new blazor -o CarExpenses --interactivity None`. Будова дворівнева: кореневий каталог із репозиторієм, а в ньому каталог застосунку `CarExpenses/`.
- Раніше на цьому місці була консольна програма (перші фіксації); її замінено на Blazor Web App, як вимагає методичка.
- Сторінку Weather шаблону видалено разом із пунктом меню; сторінки Counter шаблон без інтерактивності не створює. У меню лишився один пункт «Головна».
- Порт: `Properties/launchSettings.json` → `profiles` → `http` → `applicationUrl` = `http://localhost:5185`.
- `.gitignore` створено командою `dotnet new gitignore` і доповнено рядками `*.db`, `*.db-shm`, `*.db-wal`, `publish/`.

### Відповіді на «Перевірте себе»
1. SDK = середовище виконання + компілятор + шаблони + команда `dotnet`; потрібне для розробки. Щоб запустити готовий застосунок на чужому комп'ютері, досить середовища виконання (або самодостатньої збірки).
2. `--interactivity None` вимикає інтерактивні режими: сервер формує готову сторінку й надсилає її браузеру, постійного з'єднання немає, `@onclick` не працює. В інтерактивному режимі компонент лишається «живим» і реагує на події.
3. Точка входу — `Program.cs`: тут створюється `WebApplication`, реєструються служби (`AddRazorComponents`), налаштовується конвеєр запитів і `MapRazorComponents<App>()`, а потім `app.Run()`.
4. У `Properties/launchSettings.json`, розділ `profiles → http → applicationUrl`.
5. `.gitignore` не пускає до репозиторію `bin/`, `obj/`, базу даних і збірки. Без нього репозиторій засмітився б десятками мегабайтів файлів, які щоразу створюються заново.
6. База — це дані, а не код: у кожного свої записи, файл змінюється під час роботи, а схему відтворюють міграції.
7. Фіксація (commit) записує стан до локального репозиторію, надсилання (push) передає зафіксоване на GitHub.

## ЛР 2. Мова C# і модель предметної області

- Основний тип `CarExpense` лежить у `Models/`, клас `public`, `Nullable` увімкнено в `.csproj`.
- **`decimal` для `Amount` і `Liters`:** гроші й літри — десяткові дроби, `double` дав би похибку двійкового подання (0,1 + 0,2 ≠ 0,3).
- **`DateOnly` для `SpentOn` і `NextServiceOn`:** важливий лише день, час доби для витрати не має сенсу.
- **`int` для `Odometer`:** пробіг рахують цілими кілометрами.
- **Необов’язкові властивості** позначено `?`: `Liters` буває лише в заправки, `NextServiceOn` — лише коли відомо дату наступного ТО, `Comment` — за бажанням.
- **`enum ExpenseKind`** (`Fuel`, `Maintenance`, `Repair`, `Insurance`, `Other`): видів витрат небагато й вони сталі. Рядок дозволив би «Пальне», «пальне», «Бензин» для одного й того самого, а з enum група завжди одна.
- **Дві зіставні властивості** — `SpentOn` і `NextServiceOn`: наступне ТО не може бути раніше за дату витрати (перевірка в ЛР 6). Дата `SpentOn` потрібна для групування за місяцями в ЛР 9.
- **Особливість проєкту** — експорт звіту у CSV (описано в README).

### Відповіді на «Перевірте себе»
1. `decimal` точно зберігає десяткові дроби, а `double` — наближено у двійковому вигляді, тож у сумах накопичується похибка.
2. `?` дозволяє відсутність значення; у базі такий стовпець стане `NULL`-допустимим.
3. Властивість — пара методів get/set; `{ get; set; }` створює їх разом із прихованим полем.
4. `Id` — первинний ключ, його значення надає база під час додавання запису.
5. `DateOnly`, бо час витрати не потрібен; `DateTime` змусив би зберігати й порівнювати зайві години.
6. `enum` доречний для сталого переліку станів: компілятор не дасть записати значення, якого немає, і групування буде надійним.

## ЛР 3. Entity Framework Core і SQLite

- Додано пакети `Microsoft.EntityFrameworkCore.Sqlite`, `…Design`, `Microsoft.VisualStudio.Web.CodeGeneration.Design`, `QuickGrid` і `QuickGrid.EntityFrameworkAdapter` (версії `10.*`).
- Засоби `dotnet-ef` і `dotnet-aspnet-codegenerator` встановлено в локальний маніфест. SDK 10 створив його як `dotnet-tools.json` у кореневому каталозі (а не в `.config/`, як у методичці) — працює так само, версії зафіксовані в репозиторії.
- Контекст `Data/CarExpensesContext.cs` має `DbSet<CarExpense> CarExpenses`. Фабрику контекстів зареєстровано в `Program.cs` (`AddDbContextFactory`, рядок підключення `Data Source=carexpenses.db`), там само `AddQuickGridEntityFrameworkAdapter()`.
- **Перетворення decimal потрібне**: у моделі є `Amount` і `Liters`. Без `HasConversion<double>()` SQLite зберігав би їх текстом — сортування за сумою стало б лексикографічним («1000» < «200»), а `Sum` у запиті до бази не працював би.
- Міграцію `Init` створено й застосовано; у `carexpenses.db` таблиця `CarExpenses` має стовпці за всіма властивостями (`Amount`/`Liters` — `REAL`, дати — `TEXT`, `Liters`/`NextServiceOn`/`Comment` — `NULL`-допустимі).
- Збирання дає попередження NU1901 про низьку вразливість у `NuGet.Packaging` — це транзитивна залежність пакета генератора сторінок, на роботу застосунку не впливає.

### Відповіді на «Перевірте себе»
1. Клас-нащадок `DbContext` описує базу: кожна властивість `DbSet` — одна таблиця, тому їх стільки ж, скільки таблиць.
2. Контекст не можна використовувати кількома операціями одночасно; фабрика видає окремий короткоживучий контекст на кожну операцію. Саме фабрику очікують згенеровані сторінки.
3. SQLite не має десяткового типу, тож без перетворення `decimal` зберігався б текстом: хибне сортування й неможливе підсумовування базою.
4. Ні, у C# властивість лишається `decimal`, змінюється лише спосіб зберігання.
5. Міграція — код C#, що описує зміни схеми; база — файл із даними. У репозиторії зберігають міграції, а файл бази — ні.
6. Код і схема розійдуться: запити звертатимуться до стовпців, яких у базі немає, і застосунок упаде під час виконання.
7. Зупинити застосунок, видалити `carexpenses.db` (і `-shm`, `-wal`), виконати `dotnet ef database update` — база створиться заново з усіма міграціями.

## ЛР 4. Генератор сторінок

- Генератор запущено так: `dotnet aspnet-codegenerator blazor CRUD -dbProvider sqlite -dc CarExpenses.Data.CarExpensesContext -m CarExpense -outDir Components/Pages`. Він створив `Components/Pages/CarExpensePages/` з п'ятьма сторінками: `Index`, `Create`, `Details`, `Edit`, `Delete`. Адреса переліку — `/carexpenses` (з `@page`).
- **Що довелося виправити після генератора:**
  - Генератор вимагав пакет `Microsoft.EntityFrameworkCore.Tools` («install Entity Framework core packages…»), тож його додано.
  - Генератор дописав у `Program.cs` інтерактивний режим (`AddInteractiveServerComponents`, `AddInteractiveServerRenderMode`) і `UseMigrationsEndPoint`, а також переписав `Routes.razor` і `NotFound.razor`. Ці зміни я відкотив, бо курс працює зі статичним відтворенням і зайві режими лише додали б помилок.
  - Для `Kind` (enum) генератор поставив `InputText`, і проєкт не збирався (CS1503). У `Create.razor` і `Edit.razor` поле замінено на `InputSelect` зі значеннями `Enum.GetValues<ExpenseKind>()`.
- У меню додано пункт «Витрати» (`href="carexpenses"`).
- Розбиття на сторінки зроблено посиланнями `?page=N` по 10 записів. Кнопковий `Paginator` за статичного відтворення не працює.
- **Перевірка в браузері:** запис створюється через форму, редагується (сума змінилася на 175) і видаляється; при 13 записах є «Далі» і «Назад», друга сторінка показує записи 11–13.

### П'ять місць створеного коду
1. **`@page "/carexpenses"`** — адреса сторінки. Генератор утворив її від назви типу за власним правилом множини (`CarExpense` → `carexpenses`), тому адресу треба брати з `@page`, а не вгадувати.
2. **Немає `@rendermode`** — сторінки відтворюються статично. Сервер формує HTML і забуває про сторінку, тож `@onclick` не спрацює; працюють лише посилання й надсилання форм.
3. **`@inject IDbContextFactory<CarExpensesContext> DbFactory`** — сторінка не створює фабрику сама, а отримує її з контейнера служб, де її зареєстровано в `Program.cs` (`AddDbContextFactory`). Контекст створюється викликом `DbFactory.CreateDbContext()`.
4. **`Items` у `QuickGrid`** отримує `IQueryable` (`context.CarExpenses…Skip…Take`), а не готовий список. Тому впорядкування й розбиття виконує база, а не застосунок.
5. **`EditForm` з `FormName` і `[SupplyParameterFromForm]`** — після надсилання форми платформа заповнює властивість `CarExpense` введеними значеннями. `FormName` відрізняє форму серед інших, а `OnValidSubmit` викликає збереження лише тоді, коли перевірка пройшла; після збереження `NavigateTo("/carexpenses")` повертає до переліку.

### Відповіді на «Перевірте себе»
1. Генератор створює `Index` (перелік), `Create` (створення), `Details` (перегляд одного запису), `Edit` (зміна) і `Delete` (підтвердження видалення).
2. Компонент переліку отримує запит, щоб відбір, впорядкування й розбиття передати базі, а не читати всю таблицю.
3. Точна адреса стоїть у директиві `@page` у першому рядку `Index.razor`. Генератор утворює множину за власним правилом, тому за назвою типу її не вгадати.
4. `[SupplyParameterFromQuery]` бере значення з `?page=N`. Кожне посилання відкриває нову адресу, а кнопки потребували б `@onclick`, який за статичного відтворення не працює.
5. Меню лежить у `Components/Layout/NavMenu.razor`, що входить до макета `MainLayout`. Тому посилання додається один раз для всіх сторінок.
6. Генератор не враховує, що літри потрібні лише для заправки, що наступне ТО має бути після дати витрати, і не має українських підписів. Він нічого не знає про предметну область.

## ЛР 5. Компоненти Blazor

- **Компонент `Components/ExpenseCard.razor`** — картка витрати. У ній показано назву, вид українською (бейдж), суму, дату й пробіг, а за потреби ще літри, дату наступного ТО й коментар.
  - Параметр даних: `Expense` (`[Parameter, EditorRequired]`).
  - Параметри вигляду: `Caption` (підпис над карткою) і `ShowDetails` (показувати подробиці, за замовчуванням `true`).
- Назви видів українською дає розширення `ExpenseKind.ToUkrainian()` у `Models/ExpenseKindExtensions.cs`, тож у розмітці не потрібен `switch`.
- До `Components/_Imports.razor` додано `@using CarExpenses.Models`.
- **Де використано компонент:**
  - `Details.razor`: `<ExpenseCard Expense="carexpense" Caption="Подробиці запису" />` — показує всі подробиці;
  - `Delete.razor`: `<ExpenseCard Expense="carexpense" Caption="Перевірте, що видаляєте" ShowDetails="false" />` — лише головне.

  Перевірено в браузері: обидві сторінки показують ту саму картку з різним набором рядків.
- **Що це спростило:** раніше `Details` і `Delete` мали по вісім пар `<dt>/<dd>` з англійськими підписами. Тепер розмітка в одному місці, і зміна в картці з'являється на обох сторінках.

### Відповіді на «Перевірте себе»
1. Razor — мова розмітки з вставками C#, якою пишуть компоненти Blazor. Тому ті самі компоненти називають і компонентами Razor.
2. Параметр даних (`Expense`) без значення не має сенсу, тому він `EditorRequired`. Параметри вигляду лише змінюють показ і мають розумне значення за замовчуванням.
3. Компонент із `@page` — це окрема сторінка з адресою. Без `@page` компонент — частина іншої сторінки.
4. Значення передають як атрибут у місці виклику (`Expense="carexpense"`). `[Parameter]` дозволяє задавати властивість ззовні.
5. `[EditorRequired]` дає лише попередження в середовищі розробки й під час збирання. Під час виконання він застосунок не зупинить.
6. `= default!` стверджує, що значення буде (вимикає попередження), а `?` у типі дозволяє його відсутність.
7. За статичного відтворення код `@code` виконується на сервері один раз, під час формування сторінки. Після надсилання HTML на сервері ніщо не чекає на натискання, тому `@onclick` не спрацьовує.
8. У компонент винесено список «підпис — значення» з `Details` і `Delete`. Тепер підписи українською й формат суми та дати задаються в одному місці.

## ЛР 6. Форми, перевірка введених даних і винятки

- **Атрибути перевірки в `CarExpense`** (повідомлення українською):
  - `Title`: `[Required]` і `[StringLength(150)]`;
  - `Amount`: `[Range(0.01, 1 000 000)]`, бо витрата не буває нульовою чи від'ємною;
  - `Odometer`: `[Range(0, 2 000 000)]`;
  - `Liters`: `[Range(0.1, 200)]` — більшого бака в легковика немає;
  - `Comment`: `[StringLength(500)]`.
- **Перевірки, які атрибутом не виразити** (у `Create.razor` і `Edit.razor`, перед збереженням):
  1. Дата наступного ТО має бути пізніша за дату витрати (`NextServiceOn > SpentOn`).
  2. Літри зазначають лише для заправки (`Kind == Fuel`).
- **Унікальний індекс** `(SpentOn, Odometer, Kind)` задано в `OnModelCreating` (міграція `UniqueExpense`). Один і той самий вид витрати того самого дня з тим самим показником одометра — це майже напевно повторне внесення того самого чека. Дві різні заправки за день матимуть різний пробіг, тож індекс їм не заважає.
- **Збереження загорнуто в `try/catch (DbUpdateException) when (… SqliteExtendedErrorCode: 2067)`**. Код 2067 — це `SQLITE_CONSTRAINT_UNIQUE`, тож решта причин не маскується. У `Edit.razor` новий `catch` стоїть перед згенерованим `DbUpdateConcurrencyException`.
- **Перевірено в браузері:**
  - порожня форма показує «Зазначте, що саме оплачено» і «Сума має бути від 0,01…»;
  - ТО з датою раніше за витрату дає червону смугу «Дата наступного ТО має бути пізніша за дату витрати»;
  - дублікат при створенні і при редагуванні дає «Такий запис уже є…» замість сторінки помилки.
- Повідомлення про невдале перетворення типу («The value '…' is not valid…») формує `EditContext`, і засобами DataAnnotations його не перекласти, тож воно лишилося англійською.

### Відповіді на «Перевірте себе»
1. Див. перелік вище. Обмеження відбивають реальні межі: сума додатна, бак не більший за 200 л, текст не безмежний.
2. `?` керує схемою бази (чи дозволено `NULL`), а `[Required]` — перевіркою форми. Для обов'язкового рядка потрібні обидва.
3. «Наступне ТО пізніше за дату витрати» стосується двох властивостей одразу, тому реалізоване кодом на початку методу збереження.
4. Перевірку в браузері легко обійти, надіславши запит напряму. Захищає лише перевірка на сервері.
5. День + пробіг + вид. Повторення цього поєднання означає, що той самий чек внесли двічі.
6. `DbUpdateException` повідомляє про будь-яку відмову бази: дублікат, порушення зовнішнього ключа, зайнятий файл. Тому причину розрізняють за кодом помилки SQLite.

## ЛР 7. Зв'язки між типами, довідники, діаграма класів

- **Довідники:** `Vehicle` (автомобіль: `Name`, `PlateNumber`) і `Place` (місце: АЗС, СТО, мийка, страхова).
- **Зв'язки:** до `CarExpense` додано `VehicleId` / `Vehicle` і `PlaceId` / `Place`; у контексті з'явилися `DbSet` `Vehicles` і `Places`.
  - Обидва зв'язки описано в `OnModelCreating` з `DeleteBehavior.Restrict`.
  - Унікальний індекс з ЛР 6 доповнено `VehicleId`: однакові дата, пробіг і вид для різних машин — це різні витрати.
- **Міграція `AddReferences`.** Старі записи мали б зовнішні ключі 0, тому базу створено заново (ЛР 3, крок 6), а дані внесено повторно: 5 автомобілів, 7 місць, 14 витрат.
- **Сторінки довідників** створено генератором окремо для `Vehicle` і `Place` (`/vehicles`, `/places`); у меню додано пункти «Автомобілі» й «Місця».
  - Генератор знову дописував інтерактивний режим у `Program.cs`, `Routes.razor` і `NotFound.razor`. Ці зміни відкочено, як і в ЛР 4.
- **Форма витрати.** У `Create.razor` і `Edit.razor` додано два `InputSelect` («Автомобіль», «Місце»), а списки довідників завантажує `OnInitializedAsync`. У `Create.razor` згенерований `OnInitialized` замінено асинхронним.
- **Назви замість ключів.** У переліку стоять стовпці «Автомобіль» і «Місце» (`Vehicle!.Name`, `Place!.Name`) з `Include`; `Include` додано також у `Details`, `Edit`, `Delete`, і картка `ExpenseCard` показує назву авто й місця.
- **Видалення довідника, який використовують витрати:** `Restrict` не дає його видалити. Без обробки це давало сторінку помилки `FOREIGN KEY constraint failed`. На сторінках видалення довідників додано `try/catch` (код SQLite 19) з поясненням «Цей автомобіль використано у витратах…»; перевірено в браузері.

**Напрямок зв'язків.** Обидва довідники — «один до багатьох»: один автомобіль (одне місце) має багато витрат. Зовнішній ключ лежить в основному типі `CarExpense`, бо кожна витрата стосується рівно однієї машини й одного місця. Навігаційних колекцій у довідниках немає (`WithMany()`), бо сторінкам вони не потрібні.

### Відповіді на «Перевірте себе»
1. Значення в окремій таблиці пишуться однаково, тож групування надійне. Якщо перейменувати автомобіль один раз, зміна з'явиться в усіх записах.
2. Зв'язок описують зовнішнім ключем `VehicleId` і навігаційною властивістю `Vehicle`. EF Core розпізнає пару за назвою «назва типу + Id».
3. Зв'язки спрямовані від витрати до довідника: ключ стоїть у `CarExpense`, бо витрата належить одному авто й одному місцю.
4. `Include` завантажує пов'язаний запис разом з основним. Без нього `Vehicle` був би `null`, і в таблиці стояло б порожнє місце.
5. Через `Restrict` база відмовить у видаленні, і користувач побачить пояснення, а не зникнення історії витрат.
6. Повторний запуск генератора для `CarExpense` перезаписав би сторінки й знищив компонент з ЛР 5 і перевірки з ЛР 6.
7. Варіант «не обрано» можливий лише тоді, коли ключ має тип `int?` з `[Required]` і є відповідна міграція. Інакше `InputSelect<int>` не розбере порожній рядок.

## ЛР 8. Запити LINQ і асинхронний доступ до даних

- **Службова властивість `TitleSearch`.** До `CarExpense` додано опис у нижньому регістрі (міграція `AddTitleSearch`). У `Up` вручну дописано `UPDATE CarExpenses SET TitleSearch = lower(Title)`.
  - Як і попереджала методичка, SQL-функція `lower` кириличні описи не змінила («Заправка» лишилася з великої).
  - Тож наявні записи перезаповнено значенням `Title`, переведеним у нижній регістр. Це те саме, що робить код C# під час перезбереження форми.
- **Заповнення під час збереження:** у `Create.razor` і `Edit.razor` перед збереженням стоїть `CarExpense.TitleSearch = CarExpense.Title.ToLowerInvariant()`.
- **Сторінка переліку.** Запит будує й виконує `LoadAsync()` в одному блоці `await using`.
  - Пошук за описом нечутливий до регістру: `TitleSearch.Contains(s)`.
  - Фільтр за автомобілем: `VehicleId`.
  - Впорядкування: за датою (нові спершу, за замовчуванням), за сумою або за описом.
  - Умови беруться з адреси (`[SupplyParameterFromQuery]`), а форма `method="get"` їх зберігає.
  - Посилання «Назад/Далі» передають усі умови (`PageUrl`).
  - Поле `context`, `DisposeAsync` і `@implements IAsyncDisposable` прибрано.
- **Перевірено в браузері:** `/carexpenses?search=ЗАПРАВКА&vehicleId=1&sort=amount` показує лише заправки Skoda Octavia від більшої суми до меншої (1520 → 1380). Великі літери в запиті не заважають.

### Перевірка асинхронності
Пошуком по всіх файлах шукав `ToList(`, `First(`, `FirstOrDefault(`, `SaveChanges(`, `.Any(`, `.Result`, `.Wait(` і `CreateDbContext()`. Виправлено:
- **`CarExpensePages/Create, Details, Edit, Delete.razor`:** `using var context = DbFactory.CreateDbContext()` замінено на `await using var context = await DbFactory.CreateDbContextAsync()`; синхронний `CarExpenseExists` (`Any`) замінено на `CarExpenseExistsAsync` (`AnyAsync`).
- **`VehiclePages/…` і `PlacePages/…`:** ті самі заміни.
- **`CarExpensePages/Index.razor`:** уже `ToListAsync`.

Лишилися `CreateDbContext()` в `OnInitialized` сторінок переліку довідників: там лише створюється контекст для `QuickGrid`, а самі запити `QuickGrid` виконує асинхронно через адаптер EF.

### Відповіді на «Перевірте себе»
1. `IQueryable` перекладається на SQL і виконується базою. `IEnumerable` виконується в пам'яті над уже завантаженими об'єктами.
2. З `ToList` перед `Where` база віддасть усю таблицю, а відбір піде в пам'яті. На 14 записах це непомітно, на десятках тисяч — повільно.
3. Запит виконується відкладено. Якщо контекст уже звільнено, перебирання `IQueryable` дасть `ObjectDisposedException`.
4. У SQLite `lower` і `instr` (`Contains`) не знають кирилиці. Тому зберігається окрема властивість у нижньому регістрі. Інший спосіб — власне правило зіставлення (`SqliteConnection.CreateCollation`).
5. Після міграції в старих записах `TitleSearch` був `lower(Title)`, тобто з великою «З». Виправлено перезаповненням значенням `Title.ToLowerInvariant()`.
6. Поки база відповідає, потік обслуговує інші запити. `.Result` блокує потік і під навантаженням вичерпує пул потоків.

## ЛР 9. Сторінка зведень

- **Обчислення** винесено в `Services/SummaryCalculator.cs`: це `public static class`, що приймає `IQueryable<CarExpense>` і повертає готові рядки (`record SummaryRow`, `record FuelRow`).
  - `ByVehicleAsync` — кількість і сума витрат за автомобілем (довідник);
  - `ByMonthAsync` — кількість і сума за місяцями (період). Назва «MM.yyyy» складається вже після `ToListAsync`, бо форматування рядка SQLite не перекладає;
  - `TotalAsync` — загальна кількість і сума;
  - `FuelByVehicleAsync` — показник саме моєї теми: витрата пального на 100 км і вартість кілометра.
- **Як рахується пальне:** база віддає суму літрів, найбільший і найменший пробіг, витрати на пальне й усі витрати. Тоді `FuelRow` обчислює `л/100 км = літри × 100 / пробіг` і `грн/км = усі витрати / пробіг`.
  - Це наближення: перша заправка теж іде в літри, хоча відрізок «до неї» не враховано. На довгому проміжку похибка зменшується.
  - Перша версія будувала `FuelRow` й сортувала за ним просто в запиті. EF відповів «could not be translated», тож запит переписано: база повертає анонімний тип із числами, а record і сортування — вже в пам'яті.
- **Сторінка `/summary`** («Зведення» в меню) має три таблиці: за автомобілями з підсумковим рядком «Усього», за місяцями, і пальне та вартість км. Коли витрат немає, замість таблиць видно повідомлення з посиланням «Додайте першу витрату».
- **Перевірка, що рахує база:** тимчасово увімкнув `LogTo(Console.WriteLine, LogLevel.Information)`. У консолі видно `SELECT "v"."Name", COUNT(*), COALESCE(SUM("c"."Amount"), 0.0) … GROUP BY "v"."Name"`, тобто групує й підсумовує база. Після перевірки `LogTo` прибрано.
- **Результат на тестових даних:** Skoda Octavia — 11 витрат, 15 435 грн; Renault Logan — 3 витрати, 3 540 грн; усього 14 витрат, 18 975 грн. За місяцями: 09.2026 — 11 550 грн, 10.2026 — 7 425 грн. Пальне: Skoda — 4,0 л/100 км і 4,98 грн/км, Logan — 6,5 л/100 км.

### Відповіді на «Перевірте себе»
1. Три показники: витрати за автомобілями (на яку машину йдуть гроші), за місяцями (динаміка) і загальна сума. Окремо додано витрату пального та вартість кілометра, бо про це й тема.
2. Групування в базі передає лише готові рядки зведення, а не всі записи. Без цього обсяг даних зріс би в стільки разів, скільки записів припадає на групу.
3. Обчислення не залежать від сторінки, тож їх легко тестувати (ЛР 12) і використовувати повторно, наприклад у вебсервісі (ЛР 11).
4. `record` порівнюється за значеннями, оголошується одним рядком і незмінний. Для рядка зведення, який лише показують, це зручно.
5. Інтерпольований рядок з форматом SQLite не перекладає («could not be translated»). Тому в базі рахуються числа рік і місяць, а текст складається після `ToListAsync`.
6. Увімкнув журналювання запитів EF і побачив у SQL `GROUP BY` та `SUM`.
7. На порожній базі сторінка показує повідомлення «Витрат ще немає…» з посиланням на створення.

## ЛР 11. Вебсервіс і OpenAPI

- **Пакети:** `Microsoft.AspNetCore.OpenApi` (10.*) і `Scalar.AspNetCore` (2.18.5).
- **Тип для передавання даних** `Api/CarExpenseDto` (record) містить лише потрібні клієнтові поля, а автомобіль і місце в ньому — назвами, без навігаційних властивостей. Так у JSON немає циклічних посилань, і назовні не виходить службова `TitleSearch`.
- **Група `/api` у `Program.cs`:**
  - `GET /api/carexpenses` — перелік витрат, нові спершу;
  - `GET /api/carexpenses/{id}` — одна витрата; `Results<Ok<CarExpenseDto>, NotFound>` → 404, якщо такої немає;
  - `GET /api/summary` — зведення за автомобілями (`SummaryRow` з ЛР 9).
- **Відповідь 404.** Шаблон мав `UseStatusCodePagesWithReExecute("/not-found")`, і порожній 404 вебсервісу підмінявся б HTML-сторінкою. Тому сторінку «не знайдено» ввімкнено лише для адрес поза `/api` (`UseWhen`), і вебсервіс віддає чистий код 404.
- **Опис OpenAPI** (`/openapi/v1.json`) і сторінка перегляду Scalar (`/scalar`) підключені лише в середовищі Development.
- **Особливість проєкту — експорт у CSV:** `GET /export/carexpenses.csv?search=…&vehicleId=…`, кнопка «Завантажити CSV» на сторінці переліку.
  - Код лежить у `Services/CsvExporter.cs`. Роздільник — `;`, числа з комою, на початку стоїть BOM, тож Excel з українськими налаштуваннями відкриває файл одразу з кирилицею. Значення з `;` або лапками беруться в лапки за правилами CSV.
  - Експорт враховує ті самі умови пошуку й фільтра, що й перелік на екрані.
  - Ця точка — не частина вебсервісу (`ExcludeFromDescription`), а файл для людини.
- **Перевірка** (запити з `CarExpenses.http`, виконані curl-ом):
  - `/api/carexpenses` → 200, JSON-масив;
  - `/api/carexpenses/1` → 200, одна витрата;
  - `/api/carexpenses/99999` → **404** без тіла;
  - `/api/summary` → 200, `[{"name":"Skoda Octavia","count":11,"total":15435},…]`;
  - `/openapi/v1.json` → 200;
  - `/scalar` → 200 (через перенаправлення на `/scalar/`);
  - CSV → 200, `text/csv`, `attachment; filename=car-expenses-2026-10-29.csv`, перший рядок — заголовки українською.

### Відповіді на «Перевірте себе»
1. Вебсервіс віддає дані (JSON) для іншої програми: мобільного клієнта, звіту чи стороннього сервісу. Сторінка ж віддає HTML для людини.
2. Тип предметної області має навігаційні властивості (цикли в JSON) і службові поля, які назовні не потрібні. DTO містить рівно потрібне.
3. `Program.cs` складається з інструкцій верхнього рівня, і оголошення типу перед ними дає помилку CS8803.
4. Фабрику контекстів підставляє платформа: це параметр функції кінцевої точки, який береться з контейнера служб.
5. 404 означає «ресурс не знайдено». `TypedResults` дає типізований результат, тож його вигляд сам потрапляє в опис OpenAPI; `Results` повертає просто `IResult`.
6. У `/openapi/v1.json` точка `/api/carexpenses/{id}` має відповіді 200 зі схемою `CarExpenseDto` і 404. Їх узято з типу повернення `Results<Ok<CarExpenseDto>, NotFound>`.
